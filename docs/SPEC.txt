1. Product summary
Forge is a web platform where people learn every kind of IT skill, prove it under fair conditions,
and get hired for it. It covers algorithms, debugging, code review, SQL, security, Linux and
DevOps, backend, frontend and AI-era skills.

Principles every phase must respect
•
Practice is relaxed; Competitive is verified. AI help is fine in Practice. Only Competitive
results change ratings and appear as verified.
•
Real-work skills matter as much as algorithms. Debugging, reviewing and fixing are
first-class formats.
•

questions and an integrity score, never on single-signal bans.
•
Untrusted code never runs next to user data. The runner is a separate system on
separate hosts.
•
Fair to users. No webcam, no dark patterns, clear consent, easy data export and deletion.

API conventions
•
REST under /api/v1, JSON, OpenAPI document generated from the code and published at
/api/docs in development only.
•
Every request body, query and response is validated with zod schemas shared from
packages/shared.
•
Errors use one shape: { error: { code, message, details? } } with stable codes (for
example PLAN_REQUIRED, RATE_LIMITED).
•
Pagination is cursor-based. Lists never return more than 100 items.
•
Idempotency keys on every create action that could be retried (submissions, purchases,
invites).
•
All times stored in UTC; users choose a display time zone.

3. Security requirements
These apply to every phase. Phase L12 and each release's hardening phase verify all of them
with evidence.
3.1 Accounts and sessions
•
Passwords hashed with argon2id; minimum 10 characters; checked against a list of known
breached passwords (k-anonymity range check or a bundled list).
•
Sessions are server-side, referenced by an HttpOnly, Secure, SameSite=Lax cookie; rotated
on login and privilege change; revocable from Settings.
•
OAuth sign-in with GitHub and Google using PKCE and the state parameter.
•
Email verification required before submitting to Competitive or posting in Community.
•
Optional TOTP two-factor authentication for everyone; required for admins, moderators and
company owners.
•
Login, signup, password reset and verification are rate-limited per IP and per account, with
lockout backoff.
3.2 Web and API
•
CSRF protection on all state-changing requests (SameSite cookies plus a CSRF token header).
•
Strict Content-Security-Policy with nonces; no inline scripts; frame-ancestors none except the
lab and preview iframes, which use a separate sandbox domain.
•
User-generated content (markdown in discussions, solutions, problem statements) is rendered
with a strict sanitizer; no raw HTML.
•
Authorization checked in the API for every resource (ownership, organization membership,
role, plan). Never rely on the UI hiding things.
•
Rate limits on every endpoint class (reads, writes, submissions, searches), stricter for
anonymous users.
•
Security headers: HSTS, X-Content-Type-Options, Referrer-Policy, Permissions-Policy.
3.3 Secrets and infrastructure
•
No secrets in the repository. Local development uses .env files that are git-ignored;
production uses the host's secret store.
•
The runner hosts have no database credentials. They pull jobs from a dedicated Redis with a
restricted user and return results by signed HTTPS callback (HMAC with a rotating key).
•
Database, Redis and object storage are not reachable from the internet.
•
Admin panel requires 2FA, is audit-logged, and uses separate admin roles (content editor,
moderator, support, superadmin).
•
Automated dependency scanning and secret scanning in CI; high or critical findings block
merges.
•
Daily encrypted database backups, kept 30 days, with a tested restore procedure.
3.4 Content and flags
•
Hidden tests, reference solutions and competitive templates never leave the server.
•
Security flags are per user: FORGE{HMAC(secret, userId + challengeId)[0:24]}. A flag
submitted by the wrong user is recorded as a sharing signal.
•
Downloadable challenge files are served through short-lived signed URLs.

5. Problem packages (content format)
Every problem is a folder in content/problems/, validated by the problem-kit CLI and imported
into the database. Content lives in git so changes are reviewed like code.
Package layout
 
content/problems/two-sum-orders/
  problem.yaml          metadata (below)
  statement.md          text with {{placeholders}} filled from the generated instance
  generator.ts          (seed) => instance: data, names, planted bug, expected results
  tests.ts              (instance) => visible tests + hidden tests
  reference/            correct solutions per language (never shown to users)
    solution.py  solution.ts
  starter/              starter code per language (fix-code formats include the bug)
  hints.md              exactly 4 levels: nudge, approach, pseudocode, solution
  editorial.md          idea, why it works, complexity, common mistakes
  followups.ts          (instance, userCode) => follow-up questions (verified mode)

Validator rules (problem-kit validate)
•
Runs every reference solution against tests for at least 50 random seeds; all must pass within
limits.
•
Runs starter code and known-wrong solutions (in wrong/) and confirms they fail, so tests
actually catch mistakes.
•
Checks the generator is deterministic (same seed, same instance) and that instances really
differ between seeds.
•
Checks statement placeholders all resolve, hints have 4 levels, editorial exists, and tags are
from the allowed list.
•
Fails the CI build if any problem is invalid.
Other content types
•
Lessons: MDX files in content/courses/<course>/ with frontmatter (title, order, concepts)
and embedded exercise blocks that reference a small problem package.
•
Visualizers: React components in apps/web driven by a step list produced by instrumented
reference code.
•
Flag challenges: the package holds the downloadable files and a generator that embeds the
per-user flag where needed.
•
Review challenges: a diff plus a list of planted issues (line range + issue type) to grade
against.
Content is the product. Claude Code can draft problems in this format, but every problem
must be read and solved by a human before publishing. Budget real time for this: 150 good
problems is weeks of review work.

6. Code runner and live labs
The runner is the highest-risk component. It executes code written by strangers, so it is designed
as if every submission is an attack.
6.1 Runner design
•
Runs on dedicated VMs with no database access, no cloud credentials, and outbound traffic
blocked except to the job Redis and the API callback URL.
•
Pulls jobs from BullMQ; each job contains language, code, tests and limits, signed by the API.
•
Each run starts a fresh container from a pinned per-language image using the gVisor runtime:
--network none, read-only root filesystem, a small tmpfs work directory, non-root user, all
capabilities dropped, seccomp default profile, no-new-privileges.
•
Limits: CPU time and wall time, memory, process count (pids limit), output size, file size.
Exceeding a limit returns a clear verdict (Time Limit, Memory Limit, Output Limit).
•
Containers are destroyed after every run; nothing is reused between users.
•
Results are posted back with an HMAC signature and a job ID; the API rejects unsigned or
replayed results.
•
SQL problems run against a disposable PostgreSQL inside the sandbox, loaded with the
instance's data, with a statement timeout.
6.2 Verdicts
 Verdict
Meaning
Accepted
All tests pass within limits
Wrong Answer
At least one test output differs (visible tests show the diff; hidden
tests show only which category failed)
Time Limit / Memory Limit /
Output Limit
A limit was exceeded
Runtime Error
The program crashed; the error message is shown for visible tests
Compile Error
The code didn't compile (compiled languages)
Internal Error
Runner fault; the submission is retried once and never counts
against the user
6.3 Live labs (v1)
•
A separate orchestrator on separate lab hosts starts one container per user session from a lab
image, on its own isolated network with no internet access.
•
The user reaches it through a WebSocket terminal gateway (xterm.js) or, for web-app labs, a
reverse proxy on a separate lab domain, both authenticated with a short-lived signed token.
•
Sessions end after 60 minutes (extendable once) or 15 minutes idle, and the container and its
network are destroyed.
•
Checks for terminal tasks run inside the lab and report the target state to the orchestrator.
•
Per-user and global concurrency caps protect costs.

6.4 Security testing of the runner
Phase L4 must include an attack test suite that tries to: open network connections, read host
files, fork-bomb, fill the disk, allocate huge memory, run forever, escalate privileges, and escape
via known container techniques. Every test must be contained and produce the right verdict, with
the host unaffected.
7. Integrity system (verified mode)
Verified challenges are how Forge earns employer trust. The system makes cheating slow, risky
and visible, and never bans on a single signal.
7.1 Attempt flow
1
Consent screen listing what's recorded; no webcam.
2
Server creates an Attempt with a random seed; the generator builds a unique instance;
hidden tests and expected answers are computed server-side.
3
Full-screen workspace with a visible timer (the problem's time budget, default 45 minutes).
4
The client records events and sends them in batches every 5 seconds; the server stores them
compressed.
5
On submit: hidden tests, quality checks (linters, security scanners), then 2–3 follow-up
questions, 90 seconds each.
6
The integrity score is computed; the attempt becomes verified, unverified, or sent to review.
7.2 Recorded events
 Event
Payload
edit
Changes as small diffs with timestamps (enough to replay typing)
paste
Length, whether the content came from inside the editor, first 200
characters hashed
run / test / submit
Code hash and results
focus / blur / visibility
Time the workspace lost and regained focus
fullscreen exit
Timestamp
follow-up answer
Question ID, answer, time taken
7.3 Follow-up question types
•
Predict: "What does your function return for this input?" The server runs the user's own code
to get the true answer.
•
Edge case: "Does your code handle an empty list correctly? Yes or no." The server tests it.
•
Change: "If the rule changed to X, which line would you edit?" Graded against lines that
depend on that rule.
•
Explain choice: multiple choice about a structure the user actually used (map, sort,
recursion).

# Forge - rules for Claude Code
 
The full specification is docs/SPEC.pdf. Read the sections a phase references before
starting. If this file and the spec disagree, stop and ask.
 
## How to work
- One phase at a time, in order. Never start a phase I didn't ask for.
- Before coding: restate the phase goal, list files to create/change, list risks.
- Tests first for security-sensitive work (auth, permissions, runner, billing, integrity).
- A phase is done only when lint, type-check, unit, integration and e2e tests all pass.
  Show the command output.
- End every phase with: what was built, what's untested, what needs my manual action.
- Ask before adding a dependency not named in the spec. Use current stable versions only;
  look them up, never invent version numbers, no pre-releases.
- Small commits with clear messages. Record significant decisions in docs/decisions/.
 
## Security rules (never break)
- No secrets in git. .env files are git-ignored; document variables in .env.example.
- Authorization is checked in the API for every resource. The UI never decides access.
- Plan limits only through EntitlementsService and packages/shared/plans.ts.
- Validate every input with zod schemas from packages/shared.
- Untrusted code runs only in apps/runner sandboxes on isolated hosts. Never exec user code
  in the API or web app.
- Hidden tests, reference solutions and competitive templates never leave the server.
- Sanitize all user-generated markdown. No raw HTML rendering.
- AI features are never available during verified attempts, contests or duels.
- Never log passwords, tokens, session IDs, full emails or code from verified attempts.
 
## Conventions
- TypeScript strict everywhere. No `any` without a comment explaining why.
- API errors: { error: { code, message, details? } } with stable codes.
- Money in integer minor units with currency codes. Times in UTC.
- UI: shadcn/ui components and tokens from packages/ui; dark and light themes; WCAG 2.2 AA.
- Content: problem packages must pass `pnpm problems:validate`; drafted content gets
  status: needs-review until I approve it.
## Commands
- pnpm dev                 start everything locally
- pnpm lint && pnpm test   lint, types, unit and integration tests
- pnpm test:e2e            Playwright tests
- pnpm problems:validate   validate all content packages
